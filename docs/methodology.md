# Digi Twin — Methodology

## 1. Problem framing

Most disease-risk tools score a patient once, from a single snapshot of data.
A digital twin is different: it holds one evolving `PatientState` per patient
and re-scores that state every time new data arrives, so risk is a
continuously updated line rather than a single number. Digi Twin implements
this for the **cardiac** organ system, behind a multi-patient Streamlit app.

## 2. Architecture

![Architecture](architecture.png)

On every `tick()`:

1. `DummySimulator` emits one vitals reading (heart rate, SpO2, resting BP).
2. The twin engine (`twin_engine/`) appends it to that patient's rolling
   vitals buffer on `PatientState`.
3. `CardiacModule` rebuilds the model's feature row, scores it, and stores the
   result (plus a SHAP explanation) in `risk_scores["cardiac"]`.
4. `app.py` renders the latest state and logs an alert when the score crosses
   the threshold.

The diagram is generated by `docs/make_architecture.py`.

## 3. Data

| Item | Source | Notes |
|---|---|---|
| Training data | UCI Cleveland Heart Disease dataset, mirrored at `data/cardiac/cleveland_heart.csv` | 303 rows; rows with missing values are dropped before training. Reused from the author's `heart-disease-predictor` project |
| Live vitals | `DummySimulator` (synthetic) | There is no real wearable or EHR feed |

## 4. Model

**Classifier.** XGBoost (`n_estimators=200, max_depth=5, learning_rate=0.05,
subsample=0.8, colsample_bytree=0.8`) trained on the 13 standard Cleveland
features: age, sex, cp, trestbps, chol, fbs, restecg, thalach, exang, oldpeak,
slope, ca, thal. The target is binarised (`diagnosis > 0`). Features are
standardised with `StandardScaler`, using an 80/20 stratified split. The
held-out AUC-ROC is about 0.92 on this build's own split (the original reused
app reported about 0.94 on its own split; same model family and
hyperparameters, different split, so the two are not directly comparable).
The trained model and scaler are cached under `modules/cardiac/artifacts/`
(gitignored) after the first run.

**Explainability.** A `shap.TreeExplainer` runs on every tick, so each score
ships with its per-feature contributions. The dashboard shows the top three
by absolute contribution as a bar chart.

**Rolling features.** The model expects a static 13-field snapshot, but a
wearable can only keep two of those fields fresh. `modules/cardiac/rolling_features.py`
therefore builds each row like this:

- `trestbps` is the average resting BP over the last 10 vitals readings.
- `thalach` is the maximum heart rate over the last 10 vitals readings.
- All other fields (age, sex, cp, chol, fbs, restecg, exang, oldpeak, slope,
  ca, thal) come from the patient's EHR baseline.

SpO2 is shown on the dashboard but is **not** a model input.

## 5. Simulator

The simulator produces a bounded random walk for resting BP and mostly
ordinary heart-rate values, with occasional brief exertion spikes. It also
starts short "stress episodes" (about 2% chance per tick, lasting 8-15
ticks) in which resting BP climbs while heart rate stays low. That pattern
(chronotropic incompetence) is a real risk marker and is reflected in the
Cleveland data as low `thalach` with high `trestbps`, so the cardiac risk
score genuinely moves during a demo instead of sitting flat.

## 6. Alerts

The alert threshold lives in one place, `config.py`
(`CARDIAC_ALERT_THRESHOLD = 0.6`). In `app.py`:

- The sidebar alert log is **edge-triggered**: it records an entry only when
  a patient's score crosses from below to at-or-above the threshold, not on
  every tick it stays high.
- While the score is at or above the threshold, a flashing banner with a
  best-effort audio beep replaces the normal status banner
  (`dashboard/cardiac_alarm.py`). Browsers may block autoplay audio, so the
  flashing banner is the alert that is always visible.

## 7. Personalization

Each patient owns an independent `PatientState` (EHR profile, rolling vitals
buffer, risk scores). The model instance is shared, but it only reads the
selected patient's own state, so two patients with different EHR profiles and
reading streams produce different, independently evolving risk trajectories.
This is verified in `tests/test_engine.py::test_multi_patient_personalization`.

## 8. Validation

`tests/test_engine.py` (run with `python3 tests/test_engine.py`; no pytest
needed) covers four checks:

1. **Parity.** The cardiac module's output matches the underlying model
   called directly on the same input.
2. **Multi-day consistency.** A 60-tick simulated run keeps the history buffer
   bounded and `last_updated` monotonic, with no state corruption.
3. **Threshold-breach alerts.** A high-risk profile crosses the alert
   threshold; a low-risk profile stays under it.
4. **Multi-patient personalization.** Two distinct patients get distinct,
   correctly ordered risk scores from the same engine.

CI (`.github/workflows/ci.yml`) runs flake8 and this suite on every push and
pull request to `main`.

## 9. Limitations

- The Cleveland dataset is small (about 300 rows, roughly 297 after dropping
  missing values) and dates from 1988. Reported AUC is on a single held-out
  split of that data.
- The simulator generates plausible but synthetic time series. There is no
  real wearable or EHR integration.
- The static EHR fields never change during a session; only `trestbps` and
  `thalach` react to the vitals stream.
- Hackathon-scope prototype: no authentication, no persistence (state lives in
  the Streamlit session), and no real patient data. **Not intended for
  clinical use.**
